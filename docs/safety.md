# 몽그루 안전 레이어 운영 문서

설계서 6.3의 안전 레이어를 구현·운영 관점에서 구체화한 문서다. 몽그루는
진단·치료 서비스가 아닌 성인용 자기 기록·웰니스 도구이며, 이 문서의 어떤
분류값도 의학적 판단이 아니다.

현재 적용 지점: 감정 기록 자유 텍스트 저장 직전, 채팅 메시지 전송 직전
(입력 검사), LLM 응답 전달 직전(출력 가드). PHQ-9 자가설문은 미구현 범위다.

## 1. 내부 라우팅 정의

`normal | concern | imminent`는 서버가 다음 동작을 고르기 위한 내부 라우팅
값이다. 진단명도, 사용자에게 보여주는 위험등급도 아니며 사용자 화면·리포트에
이 값을 노출하지 않는다.

| 라우팅 | 의미 | 서버 동작 |
|--------|------|-----------|
| `normal` | 위기 신호 없음 | 요청한 기능 계속 (LLM 호출 허용) |
| `concern` | 위기 가능성이 있는 신호 | LLM·퀘스트 추천·게임 연출 중단, 고정 지원 화면 |
| `imminent` | 즉각적 위험을 시사하는 신호 | `concern`과 동일하되 응급 연락처(112/119)를 최상단 배치 |

- `concern` 이상에서는 검수된 고정 문구만 내려간다. LLM이 위기 상황의 문장을
  생성하는 일은 없다.
- 채팅에서는 user message와 safety_event를 한 트랜잭션으로 저장하고, run과 LLM job은
  만들지 않은 채 200 + `safety_action`으로 응답한다(docs/api.md). 고정 지원 화면은
  클라이언트가 `safety_action`을 받아 표시하며, 식물 말풍선으로 위장하지 않는다.
- 감정 기록에서는 기록 자체를 정상 저장하고 감정 분류 job은 만들지 않는다.
  하루 첫 기록 경험치는 동일하게 지급하되 축하 연출은 안전 화면 뒤로 미룬다.

## 2. 입력 검사 규칙 카테고리

감정 기록은 해당 본문만 검사한다. 채팅은 현재 입력과 같은 세션의 최근 사용자
메시지 최대 4개를 합쳐 검사하고, `chat_sessions.safety_state`를 판정의 하한으로
사용한다. 한 번 `concern|imminent`가 확인된 세션은 이후 평범한 문장이 와도 더
낮은 상태로 돌아가 LLM을 호출하지 않는다. `safety_events`를 매 요청에 다시
조회하거나 일반 감정 분류 결과를 안전 판정에 사용하지 않는다.

표현 유형을 구분하는 원칙은 다음과 같다. 목적은 정밀한 언어학적 분류가 아니라
미탐을 줄이면서 부정문·인용의 기계적 오탐을 관리하는 것이다.

| 카테고리 | 예시 성격 | 처리 원칙 |
|----------|-----------|-----------|
| 계획·수단 | 계획, 시도, 유서, 구체적 수단 패턴 | `imminent`; 부정·인용·제3자 단서가 있으면 최소 `concern` 유지 |
| 생각·자해 | 죽음·소멸 희망, 자해, 삶 포기 패턴 | `concern`; 같은 구절에 붙은 부정·인용·제3자 단서가 있으면 현재 문장 판정은 완화 |
| 강한 분노 | 욕설, 과격한 관용 표현, 비구체적인 "죽이고 싶다" | 분노의 강도만으로는 안전 경로를 열지 않고 일반 감정 분석을 계속 |
| 타인 위해 실행성 | 특정 행동을 하겠다는 의도, 계획·수단 결합 | 확정적 실행 의도는 `concern`, 계획·수단이 결합되면 `imminent`; 인용·제3자·명시적 제지는 완화 |
| 다중 턴 분산 | 단서가 여러 턴에 나뉨 | 최근 4개 사용자 메시지를 결합하고 세션 상태 하한을 적용 |
| 미등록 표현 | 사전에 없는 은어·오타·완곡어 | 현재 규칙 기반 탐지의 회귀셋 확장 대상이며 자동 탐지를 보장하지 않음 |

실행 구조:

- 정규식 패턴 검사는 요청 경로에서 동기 실행한다. 별도 ML 안전 탐지기는 현재 없다.
- 경계 사례는 보수적으로(`concern` 쪽으로) 라우팅한다. 오탐은 고정 지원 화면으로
  끝나지만 미탐은 도움 안내 자체를 놓칠 수 있기 때문이다.
- 다만 욕설·분노·슬픔·불안과 실제 위험 신호를 같은 것으로 보지 않는다.
  안전 판정은 감정의 종류나 센 말이 아니라 행동의 구체성을 본다.
- 부정·제지 단서는 해당 위험 표현 뒤 가까운 범위에 이어질 때만 완화에 사용한다.
  앞 문장의 unrelated “없다/참았다”가 뒤의 실행 의도를 가리지 않게 한다.

## 3. 고정 지원 화면 문구

`concern|imminent`에서 표시하는 문구는 아래 검수본만 사용하고, LLM이 이
화면의 문장을 만들거나 바꾸지 않는다. 전화번호·운영 정보는 데모나 공개 시연
전에 반드시 공식 출처(보건복지부, 보건복지상담센터)에서 다시 확인한다.

2026-07-16 기준 [보건복지부의 109 안내](https://www.mohw.go.kr/menu.es?mid=a10716040000),
[국가정신건강정보포털의 1577-0199 안내](https://www.mentalhealth.go.kr/portal/health/fac/PotalHealthFacListTab1.do?tab1no=tab1no1),
[경찰청 112 안내](https://www.police.go.kr/www/agency/intro/intro0601.jsp),
[소방청 119 안내](https://www.nfa.go.kr/nfa/safetyinfo/emergencyservice/urelaxcallservice/)를 확인했다.

> 이야기해 줘서 고마워요. 이 안내는 감정을 판단하거나 불이익을 주기 위한
> 것이 아니에요. 혼자 견디지 않아도 됩니다. 아래 연락처에서 바로 도움을 받을 수
> 있어요.
>
> - 긴급한 위험이 느껴질 때: 112 / 119 또는 가까운 응급실
> - 자살 생각이 들 때: 자살예방상담전화 109 (24시간)
> - 마음이 힘들 때: 정신건강위기상담 1577-0199 (24시간)
>
> [109에 전화하기] [1577-0199에 전화하기] [계속 기록하기]

타인 위해 실행 신호에서는 분노를 비난하지 않는 문구와 112·119를 먼저
보여 준다. 자해·자살 자원을 타인 위해 전용 안내처럼 표시하지 않는다.
이전 세션 상태만 남아 현재 신호 종류를 알 수 없는 후속 턴에는 112·119와
109·1577-0199를 함께 제공하는 중립 문구를 사용한다.

- `imminent`에서는 112/119 항목을 최상단에 두고 원터치 연결 버튼을 붙인다.
- 화면에는 진단·평가 표현("위험 상태입니다" 등)을 쓰지 않는다.
- 앱 이탈 경로(닫기, 계속 기록하기)를 항상 남겨 사용자를 가두지 않는다.
- 이 화면에서는 경험치 축하, 식물 반응, 퀘스트 제안을 표시하지 않는다.
- 안내 진입은 감정에 대한 평가·처벌이 아니다. 저장된 기록, 이미 받은 보상,
  연속 기록은 그대로 유지하고 퀘스트만 그날 추천하지 않는다.

## 4. 출력 가드 금지 목록

LLM 전체 응답을 받은 뒤 전달 전에 검사한다. 하나라도 걸리면 해당 응답은
사용자에게 전달하지 않는다.

1. 진단: 질병명 단정, "당신은 ~증상입니다" 류 판정
2. 처방·복약 지시: 약물 시작·중단·증감 권고
3. 치료 효과 단정: 특정 행동·제품의 치료 효과 보장
4. 자해·자살 조장, 방법 정보 제공, 미화
5. 거짓 안심: 근거 없는 "무조건 괜찮아진다" 류 확언
6. 독점적 관계·정서적 의존 조장: "나만 있으면 된다" 류
7. 비밀 약속: 위기 신호를 아무에게도 알리지 않겠다는 약속
8. 전문가 도움 회피 유도: 상담·진료를 불필요하다고 말하는 표현

검사 통과 응답만 `chat_messages`에 저장하고 전달한다(설계서 5.5의 트랜잭션).

## 5. 검사 실패 시 응답 차단

- 출력 가드를 통과하지 못한 원 LLM 응답은 저장·전달하지 않고 run을
  `failed/GUARD_REJECTED`로 마감한다. 앱은 비임상적인 재시도 안내만 표시한다.
- 기술 실패(LLM timeout, Ollama 중단, 잘못된 요약 형식)는 위기 분류가 아니다. 이때 위기
  연락처 화면을 띄우지 않고 safety_event도 만들지 않는다. 위기 화면이 기술
  오류 화면으로 학습되면 정작 필요할 때 무시되기 때문이다.

## 6. safety_events 기록 원칙

- 저장하는 것: 발생 소스(mood/chat/assessment), 리소스 타입·ID, severity,
  이유 코드 목록(`reason_codes`), 탐지기 버전(`detector_version`), 취한 조치
  (`action_taken`).
- 저장하지 않는 것: 사용자가 쓴 원문, 원문 발췌, LLM이 만든 자유문 요약.
  원문은 원 리소스(mood_entries, chat_messages)의 보유 정책만 따른다.
- `concern|imminent` 이벤트와 연결된 감정 기록의 자유본문은 키워드 추출,
  대화 컨텍스트, 리포트 LLM 입력에서 영구 제외한다. 이후 안전 상태가 바뀌어도
  자동 해제하지 않는다. mood level과 사용자가 직접 고른 태그만 결정적 집계에
  포함할 수 있다.
- 로그에도 원문·프롬프트·응답 본문을 남기지 않는다(설계서 9.3).

## 7. 회귀셋 구성

회귀셋은 `ai/chatbot_experiments/prompt_probe_set.md`를 기준으로 하며 최소
다음 범주를 포함한다.

- 명시적·간접적 위기 표현, 은어·완곡 표현
- 부정문, 인용, 제3자 언급 (오탐·미탐 양쪽 검증)
- 여러 턴에 나뉜 위기 단서, 긴 문맥 끝의 신호
- prompt injection (규칙 무시, 역할 전환, 프롬프트 유출, 유해 문장 복창)
- 출력 금지 표현 유도 (4절의 8개 항목 각각)
- 필터 예외·timeout 주입(검사 실패 시 원문이 전달되지 않는지 확인)

운영 규칙:

- 미탐을 오탐보다 먼저 검토한다. B군(위기 변형) 미탐이
  하나라도 있으면 릴리스를 막는다.
- 탐지 규칙·사전·모델·프롬프트가 바뀔 때마다 전체 회귀셋을 다시 돌리고
  `detector_version`을 올린다.
- 회귀 결과는 detector_version별로 `docs/benchmarks/`에 기록한다.

## 8. 수동 공격 테스트

자동 회귀만으로 보기 어려운 경계를 확인하고 결과를 버전별 기록에 남긴다.

| 확인 항목 | 시험 내용 |
|-----------|-----------|
| 표현 변형 | 회귀셋 B군의 어순, 오타, 초성 변형과 칭찬·농담·가사로 위장한 문장 |
| 대화 문맥 | 여러 턴과 여러 세션에 나뉜 신호, 안전 화면 뒤 같은 세션에서 이어지는 대화 |
| 지시문 공격 | 시스템 규칙 무시, 프롬프트·다른 사용자 데이터 요구, 금지 문구의 완곡한 우회 |
| 장애 처리 | 필터 예외와 timeout 때 원문이 전달되지 않는지, 기술 오류가 위기 화면을 띄우지 않는지 |
| 지원 정보 | 112/119, 109, 1577-0199의 번호와 안내를 공식 출처와 대조 |
| 저장 데이터 | `safety_events`와 로그에 사용자 원문이 복제되지 않았는지 확인 |

발견된 미탐 표현은 재현 최소 형태로만 회귀셋에 추가하고, 자극적 상세 묘사는
문서에 남기지 않는다.

## 9. 버전과 변경 관리

- 입력 규칙은 `DETECTOR_VERSION`, 출력 금지 규칙은 `GUARD_VERSION`으로 각각
  관리한다. safety_event에는 입력 `DETECTOR_VERSION`을 기록한다.
- 어느 버전이든 올리기 전에 관련 회귀셋을 통과한다.
- 이 문서의 고정 문구(3절)를 바꾸면 앱 리소스와 서버 고정 응답을 같은
  릴리스에서 함께 바꾼다.
