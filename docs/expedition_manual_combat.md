# 탐험 수호전 수동 지휘 계약

최종 갱신: 2026-08-07
상태: 첫 지역 구현 기준
관련 코드: `server/app/content/expeditions/combat.py`,
`app/lib/features/expedition/presentation/expedition_battle_panel.dart`

## 1. 문제 정의

기존 수호전은 서버가 선택 한 번으로 승패·피해·반격을 먼저
확정하고 앱이 그 결과를 재생했다. 화면이 움직여도 사용자가 판단할
순간이 없었고, 자동 순찰과 본질적으로 다르지 않았다.

수호전은 다음 질문에 대한 답이 매 라운드 달라야 한다.

1. 누가 먼저 집중력을 만들고 누가 쓸 것인가?
2. 현재 약점을 맞힐 것인가, 다음 약점을 대비할 것인가?
3. 적의 예고 공격을 누가 받고 어떻게 막을 것인가?
4. 지금 스킬을 쓰거나 방어할 때 남은 라운드 안에 장벽을 깰 수 있는가?

## 3. 확정 플레이 루프

```text
적 의도·약점 확인
  → 살아 있는 대원 전원의 행동 선택
  → 행동 순서·전열 조정
  → 예상 집중력·장벽 피해 확인
  → 명령 확정
  → 대원별 행동 연출
  → 적이 살아 있으면 예고한 공격 실행
  → 다음 라운드 또는 승리·긴급 귀환
```

- 기본은 수동 지휘다. 자동 지휘는 사용자가 켜면 해당 수호전의
  승패가 나기 전까지 유지되고, 전투를 나가면 다시 OFF로 시작한다.
- 승리 기대 시간은 입력 포함 45~90초, 3~6라운드다.
- 행동 순서는 공유 집중력의 생성·사용 순서이자 현재 전열이다.
- `front` 의도는 첫 번째 명령의 대원을 공격한다. 단순 정렬 UI가 아니다.
- 장벽을 깨면 적 공격 전에 즉시 승리한다. 끝낸 라운드의 반격은 없다.
- 6라운드가 끝나거나 전원 HP가 0이면 긴급 귀환한다. 캐릭터는 손실·퇴화하지 않지만 미확정 탐험 보상은 받지 못한다.

## 4. 자원·판정

### 공유 집중력

- 시작 3, 최대 5. 콘텐츠로 변경 가능하되 `starting_focus <= max_focus` 검증을 통과한다.
- 기본 공격과 마음 지키기는 1을 만든다.
- 고유 스킬은 2~3을 쓴다. 앞 대원이 만든 집중력을 뒤 대원이 같은 라운드에 쓸 수 있다.
- 순서상 집중력이 부족하면 앱은 확정 버튼을 잠그고 부족해지는 대원을 알린다. 서버도 422로 동일하게 거절한다.

### 상성

- `care|돌봄`, `focus|집중`, `courage|용기`, `insight|관찰` 네 공명을 쓴다.
- 현재 약점과 공명이 같으면 장벽 피해 +7. 약점은 라운드마다 콘텐츠 순환표를 따른다.
- 상성은 성공 확률이 아니라 정확한 추가 피해다. 숨은 명중·치명타 확률은 없다.

### 방어와 HP

- 대원 HP는 3. 수호자를 죽이는 표현 대신 수호 장벽을 0으로 만든다.
- 마음 지키기는 당해 라운드 피해 2를 막는다. 남은 방어는 다음 라운드로 이월하지 않는다.
- 적 의도는 `front|lowest|all`과 1~3 위력을 문장·아이콘·숫자로 동시에 보여 준다.

## 5. 캐릭터 고유성

10종 모두 서로 다른 전투 스킬과 후속 판정을 가진다.

| 품종 | 스킬 | 고유 판정 |
|---|---|---|
| baby-pot | 새싹 응원 | 전원 피해 1 방어 |
| handsome-pot | 온기 지휘 | 집중력 1 환급 |
| pretty-pot | 개화의 스텝 | 최저 HP 대원 1 회복 |
| tsundere-pot | 착각하지 마 방패 | 자신 방어 2 |
| zombie-pot | 끈질긴 붙잡기 | HP 1일 때 피해 +8 |
| gumiho-pot | 여우불 미혹 | 해당 라운드 적 위력 -1 |
| ninja-pot | 그림자 틈베기 | 약점 일치 추가 피해 +6 |
| magical-pot | 프리즘 해답 | 현재 약점 상성으로 변환 |
| aloof-pot | 냉정한 간파 | 비약점 공격에도 피해 +5 |
| student-pot | 계산된 해답 | 집중력 2 환급 |

고유 스킬은 단순 피해량 서열이 아니다. 방어·회복·자원·약화로
편성과 순서를 바꾸는 이유를 만든다.

## 6. 연출·소리·접근성

- 서버 `last_exchange` 순서대로 대원 행동을 각각 760ms, 적 행동을 940ms로 재생한다. 한 번에 모두 겹쳐 판정을 숨기지 않는다.
- 모바일 전투 무대는 4:3으로 확보한다. 현재 행동 대원은 전경 40%, 수호자는 반대편
  62%를 점유하고 나머지 대원 최대 두 명은 실제 성장형·의상·HP를 유지한 후열로 보인다.
- 수호자는 `idle → hit → attack` 또는 `idle → hit → defeated` 자세로 전환한다.
  캐릭터도 공격은 `grow`, 방어·피격은 `diary` 자세와 전진·반동 transform을 조합한다.
- 돌봄 덩굴, 불씨 호, 프리즘, 안개 돌진, 통찰 궤적, 적 기록 파동은 각각 다른 색만
  쓰는 선이 아니라 실루엣·진행 방향·충돌 파편이 구분되는 전면 Canvas 연출이다.
- 행동명과 피해 숫자는 이미 화면에서 일어난 원인과 결과를 설명하는 보조 HUD다. 텍스트가
  캐릭터·몬스터의 자세 전환과 충돌 장면을 대신해서는 안 된다.
- 대원 명령, 일반 충돌, 약점 피격, 적 공격, 방어, 승리, 패배는 서로
  다른 7종 PCM WAV를 사용한다. 외부 샘플 없이 `build_expedition_sfx.py`로
  재현 가능하게 합성한다.
- 마지막 행동은 서버 `outcome` 문구를 표시한 뒤 1,100ms 유지하고,
  승리는 상승 차임을, 패배는 하행 차임을 재생한 뒤에만 다음 화면을 연다.
- 효과음은 배경음을 끈지 않고 짧게 겹친다. 오디오 기기·자동 재생 실패는 플레이를 멈추지 않는다.
- 피격 행틱은 약 2.8~3.5px, 단일 구간에만 사용한다. 명령 선택·충돌·방어는 서로 다른 행틱 피드백을 준다.
- `disableAnimations`에서는 결과를 즉시 보이되, 행동 명·피해·방어·승패를 live region으로 읽는다.
- 색만으로 약점·피격 대상을 구분하지 않고 텍스트, 아이콘, 숫자를 같이 쓴다. 조작 표적은 최소 48dp다.
- 320px 폭·200% 글자, 화면 읽기, 움직임 줄이기는 출시 차단 검증 항목이다.

## 7. 서버 계약

- `POST /expeditions/{run_id}/combat/turns`
- 요청: 살아 있는 대원 전원의 `{member_id, action}`를 실행 순서대로 전송한다.
- `action`: `attack|skill|guard`
- 살아 있는 대원 누락, 중복, 알 수 없는 행동, 순서상 집중력 부족은 422다.
- 기존 guardian `choice`와 단독 `skill` API는 409로 거절한다. 구버전 결과형 우회로가 없어야 한다.
- `expected_revision` 충돌 검사와 `client_action_id` 멱등 재생을 기존 탐험 행동과 같이 쓴다.
- 런타임 전투 상태는 `runtime_effects_snapshot.guardian_battle`에 저장해 앱 종료·기기 변경 후에도 이어서 플레이한다.

## 8. 검증 기준

1. 명령 순서를 바꾸면 같은 행동 조합의 집중력 성공 여부와 `front` 피격 대상이 바뀐다.
2. 약점 추가 피해, 방어 차감, 회복·자원 후속 효과가 서버·앱 예상값과 일치한다.
3. 장벽 0은 허위 기본값으로 바뀌지 않고 HUD에 0으로 표시된다.
4. 승리 라운드에서 적 공격은 재생되지 않는다.
5. 연출 중 입력은 잠기고, 모든 행동 큐가 끝난 뒤에만 다음 라운드 상태를 보인다.
6. 자동 지휘 OFF가 초기값이며, ON은 현재 위험·약점·집중력을 보고 합법적인 명령만 보낸다.
7. 오디오 실패·네트워크 재시도·리비전 충돌 중에 명령이 중복 해결되지 않는다.
8. 수호전 보상은 마음 일기의 일일 XP·씨앗 보상을 넘지 않는다.

## 9. 2026-08-06 릴리스 Web 실측

- 390×844, Flutter 3.44 WebAssembly 릴리스, 로컬 실제 API·DB로 4라운드를
  수동 2회·자동 2회 직접 플레이했다.
- 수동 1라운드 4초 구간은 241프레임, 평균 16.64ms, p95 16.8ms,
  최대 16.9ms였고 25ms 초과 프레임은 0이었다.
- 명령 확정 1회당 `combat/turns` POST는 정확히 1회였고, 효과음 7종은
  모두 번들에서 200으로 로드되었으며 브라우저 콘솔 오류·경고는 0이었다.
- 연출 중에는 이전 상태를 유지하고, 대원 행동·적 반격·승패 표시가
  끝난 뒤에만 장벽·HP·집중력과 다음 의도를 한 프레임에 반영했다.

## 10. 2026-08-07 시각 전투 회귀

- 390×844 릴리스 Web과 실제 로컬 API·DB에서 수동으로 명령을 예약해
  `장벽 100 → 67 → 34 → 8 → 0` 전 과정을 다시 플레이했다.
- 전경에는 현재 행동 캐릭터, 후열에는 실제 편성 캐릭터, 반대편에는
  수호자를 동시에 유지했다. 캐릭터 전진·복귀, `idle → hit → defeated`,
  스킬 궤적, 피해 숫자, 적 반격 파동이 같은 타임라인에서 확인됐다.
- 일반 CPU 기준 평상시 3초와 전투 3초는 각각 181프레임이었고 p95
  16.8ms, 최대 16.9ms, 25ms 초과 0이었다. 표준 JS 릴리스의 최종
  처치 2.5초도 151프레임, 평균 16.63ms, p95 16.8ms, 최대 16.8ms였다.
- 처치 프레임은 900ms, 1,500ms, 1,800ms 시점까지 유지되고 2,000ms에
  결과 화면으로 전환됐다. 승리 문구와 쓰러진 자세를 읽기 전에 장면이
  사라지지 않는다.
- 최종 번들의 에셋 1,191개, 수호자 4상태 모바일 파생본, 폰트와
  매니페스트를 직접 확인했다. 앱 콘솔 오류·경고와 HTTP 404·500은 0이었다.
