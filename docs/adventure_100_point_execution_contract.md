# 모험 RPG 100점 실행 계약

최종 갱신: 2026-08-10
문서 상태: **D100 — 구현 가능한 기준 문서**
제품 상태: 아래 `9. 구현 증거 대장`에서 별도 관리

이 문서는 모험·전투·성장·에셋 문서를 실제 코드와 검수 증거로 연결하는 실행
원본이다. 화면의 방향은 `expedition_stage_redesign.md`, 성장과 밸런스는
`combat_identity_progression_design.md`, 획득·경제는
`character_skill_growth_design.md`, 제작 규격은
`design-system/EXPEDITION_ASSET_PRODUCTION.md`가 정한다. 서로 충돌하면 사용자가
직접 체감하는 전투 계약은 스테이지 개편 문서가 우선하고, **완료 여부와 증거는 이
문서만** 따른다.

> `문서 100점`은 요구사항이 빠짐없이 결정되고 구현·검수 방법까지 추적된다는
> 뜻이다. 게임이 완성됐다는 뜻이 아니다. 제품 점수는 production 에셋, 실제 기기,
> 성능, 접근성, 밸런스 증거가 있어야만 오른다.

### 1.2 D100 합격 조건

다음 조건을 모두 만족했으므로 문서 상태를 D100으로 판정한다.

1. 모든 `MUST` 요구가 코드·데이터·에셋·검수 중 하나 이상의 산출물에 연결된다.
2. `설계 완료`, `코드 완료`, `production 에셋 완료`, `출시 완료`를 섞지 않는다.
3. 서버와 앱이 공유하는 여섯 행동 코드와 구버전 호환 규칙이 결정돼 있다.
4. 짧은 탭·350ms hold·접근성 대체 action·AUTO가 같은 판정 경로를 쓴다.
5. 코드 도형·공용 파동·일괄 시트를 정식 공격 에셋으로 세지 않는다.
6. 실제 기기·성능·접근성 증거가 없으면 제품 완료로 표시하지 않는다.

## 2. 상태 용어 — 한 단어 `완료` 금지

| 상태 | 의미 | 허용 증거 |
| --- | --- | --- |
| `D` 설계 | 사용자 흐름·수치·예외가 결정됨 | 승인 문서·스키마 |
| `C` 코드 | 서버 판정과 앱 UI가 연결되고 자동 테스트 통과 | 소스 경로·테스트명 |
| `A` 아트 | 정식 에셋 gate를 통과 | manifest·contact sheet·alpha QA |
| `Q` 품질 | 실제 기기·접근성·성능 기준 통과 | 캡처·trace·측정 보고서 |
| `R` 출시 | D+C+A+Q와 배포 pack 검증 통과 | release manifest·빌드 |

`C 완료/A 미완료`는 정상적인 중간 상태다. 이때 앱은 기능적으로 동작하더라도
`prototype`이며 스토어 영상·출시 노트·완료율에 정식 전투로 넣지 않는다.

## 3. 100점 사용자 경험 불변식

1. 모험의 기본 화면은 설명 목록이 아니라 **한 카메라의 전장**이다.
2. 전투 중 상시 텍스트는 진행, HP/장벽, 집중력, 적 의도·대상·위력, 잠금 사유,
   600ms 안쪽 시전명뿐이다. 스킬 이름·효과 전문은 상시 노출하지 않는다.
3. 전장 가시 영역은 390×844 기준 화면 높이의 72% 이상이다. HUD와 명령 벨트는
   배경을 새 카드로 밀지 않고 가장자리에 겹친다.
4. 행동 대원을 고른 뒤 여섯 아이콘 중 하나를 탭하면 즉시 서버 판정과 연출이
   시작된다. 대상 자동 행동은 최대 두 탭이다.
5. 플레이어와 적 모두 `anticipation → release → travel → contact → reaction →
   recovery`를 가진다. 공격 본체가 실제로 이동하고 접촉 프레임에서 수치·SFX·햅틱이
   일치한다.
6. `약점`과 `내성`은 첫 조우부터 공정한 선택 정보로 공개한다. 생태·전체 패턴·히든
   보상은 관찰·획득 뒤 도서관에서 열린다.
7. 감정은 보상/벌점이 아니다. 여섯 성장결은 동등한 전술 언어이고 어느 결도 범용
   상위호환이 될 수 없다.
8. AUTO·2×·짧은 연출은 판정을 바꾸지 않는다. 저감 모션은 정보를 줄이지 않는다.

## 4. 전투 데이터와 API 계약 `combat-kit-v6` / `battle-state-v2`

### 4.1 고정 슬롯

| 순서 | UI 슬롯 | API `action` | 출처 | 기본 판정 |
| ---: | --- | --- | --- | --- |
| 1 | 기본 공격 | `attack` | 캐릭터 성장결 | 집중력 +1 |
| 2 | 고유 I | `unique_1` | 품종 고유 | 집중력 비용·품종 효과 |
| 3 | 고유 II | `unique_2` | 품종 고유 | 고유 I과 다른 역할 |
| 4 | 선택 I | `selected_1` | 장착 감정/기록서 | 교체 가능 |
| 5 | 선택 II | `selected_2` | 장착 감정/기록서 | 교체 가능 |
| 6 | 마음 지키기 | `guard` | 공통 | 방어 +2, 집중력 +1 |

서버는 위 여섯 값을 권위 있게 판정한다. 구버전 `skill`은 한시적으로
`unique_1`과 동일하게 해석하고 응답에는 새 슬롯을 모두 돌려준다. 앱은 새 서버에서
`skill`을 전송하지 않는다.

### 4.2 응답 스키마

```json
{
  "kit": {
    "version": 6,
    "level": 25,
    "rarity": 4,
    "signature_tier": 3,
    "primary_element": "wind",
    "affinity": "care",
    "affinity_label": "돌봄",
    "basic": {"code": "attack", "...": "..."},
    "unique_skills": [
      {"slot": "unique_1", "code": "sprout_cheer", "element": "nature", "kel": "sunny", "...": "..."},
      {"slot": "unique_2", "code": "root_embrace", "...": "..."}
    ],
    "selected_skills": [
      {"slot": "selected_1", "source": "emotion", "...": "..."},
      {"slot": "selected_2", "source": "skillbook", "...": "..."}
    ],
    "guard": {"code": "guard", "...": "..."}
  }
}
```

각 행동은 `slot, code, name, description, raw_power, power_scale_bp,
tier_power_bp, power_neutral, matchup, matchup_bp, effect_power_bp, power,
focus_cost, focus_delta, cooldown_turns, cooldown_remaining, ready_round, tier,
tier_label, element, elements, kel, kels, damage_type, motion_profile, vfx_family,
effect_key, effect, guard, source`를 가질 수 있다. 수치가 없는
필드는 `0` 또는 `null`로 직렬화한다. 피해·집중력·부가 효과는 앱이 다시 계산하지
않고 서버 결과를 최종값으로 사용한다. 앱의 예상 피해는 선택 보조 표시일 뿐이다.

### 4.3 결손·구버전·오프라인 처리

- 새 슬롯이 빠진 구버전 응답: 기본·기존 `skill`·지키기는 동작시키고 나머지 슬롯은
  잠금 glyph와 `업데이트 필요`만 표시한다. 빈 버튼을 숨겨 위치를 바꾸지 않는다.
- 알 수 없는 `effect_key`: `echo_wave` 래스터 fallback을 쓰고 판정은 유지한다.
- 아이콘 누락: 같은 공격 family의 검수된 fallback 래스터를 쓴다. 코드 유기체나
  이모지를 대신 그리지 않는다.
- 네트워크 실패: 제출한 아이콘을 원상 복귀하고 같은 행동을 재시도할 수 있게 한다.
  클라이언트가 낙관적으로 HP·장벽을 확정하지 않는다.
- 중복 탭: `interactionLocked`와 idempotency key로 한 행동만 제출한다.

### 4.4 장착과 획득의 단계적 계약

`selected_1/2`는 저장된 `combat_loadout`을 우선하고, 아직 장착 기능을 열지 않은
계정은 `성장결 기본 스킬 + 현장 기록서`를 안전 기본값으로 받는다. 이후 상점 구매,
해금 조건, 던전 획득은 동일한 스킬북 소유권 테이블에 기록한다.

- 소유권과 장착은 분리한다. 보유해도 자동 장착하지 않는다.
- 전투 중에는 장착을 바꾸지 않는다. 출발 전·캐릭터/스킬북 화면에서만 교체한다.
- 유료 캐릭터는 초기 사용감과 성장 상한을 높일 수 있지만 동일 성장 구간에서 무료
  캐릭터의 역할을 제거하거나 승률을 독점하면 안 된다.
- 밸런스 수치는 콘텐츠 버전으로 고정하고 진행 중 run은 시작 snapshot을 유지한다.

## 5. 밸런스와 성장 합격선

| 항목 | 합격 기준 |
| --- | --- |
| 캐릭터 정체성 | 고유 I은 대표 공격/지원, 고유 II는 다른 전술 역할 |
| 선택 폭 | 선택 I·II 중 하나 이상은 현재 약점 대응 또는 생존 선택을 제공 |
| 비용 | 집중력 0~5에서 최소 한 행동은 항상 합법 |
| 상성 | 약점 ×1.50, 내성 ×0.60, 최종 피해 최소 1; 색 외에 glyph와 화살표 병기 (`expedition_combat_core_design.md` 4장) |
| 가격 | 동일 레벨·성장 단계의 평균 승률 격차 5%p 이내, 역할 독점 0 |
| 진화 | 성장 단계는 외형·기본 수치·스킬 tier를 함께 올리되 이전 콘텐츠를 무효화하지 않음 |
| 실패 | 패배 시 캐릭터 소실·장비 파괴·감정 벌점 없음 |

자동 시뮬레이션은 캐릭터·성장결·장착 조합별 10,000회 이상 실행하고 P10/P50/P90
클리어 라운드, 승률, 사용 스킬 분포를 남긴다. 평균만으로 합격시키지 않는다.

## 6. UI·입력·접근성 계약

### 6.1 여섯 아이콘 벨트

- 360px 이상: 한 줄 6개. 320~359px 또는 150% 이상 글자: 3×2.
- 각 터치 영역 48×48dp 이상, 인접 영역 간 8dp를 목표로 하되 320px에서는 겹치지
  않는 것을 우선한다.
- 기본 화면에는 아이콘, 비용 링, 약점/내성 glyph, 잠금 사유 한 단어만 둔다.
- 짧은 탭은 실행, 350ms hold는 높이 40% 이하 상세 시트다. hold 뒤 손을 떼어도
  실행되지 않는다.
- 스크린리더·키보드에는 `실행`과 `상세 보기`를 별도 semantic action으로 제공한다.
- 누르는 동안 150ms 안에 `scale 0.96`; 잠금 상태는 움직이지 않는다.

### 6.2 상세 시트

상세 시트만 이름, 설명, 현재 비용, 예상 피해, 약점/내성 보정, source, tier를 보여
준다. 열려 있는 동안 전투 제출과 AUTO 타이머를 멈추고, 닫은 뒤 원래 선택 대원과
포커스를 복원한다.

### 6.3 저감 모션

저감 모션은 `release/contact/reaction` 대표 프레임을 순서대로 240~700ms 안에
보여 준다. 화면 흔들림·카메라 이동·ambient drift는 제거하지만 적 의도, 피해,
방어, 약점, 결과 callout은 유지한다.

## 7. 아트·스프라이트·오디오 gate

정식 공격 family 하나는 다음을 모두 가진다.

1. `anticipation 2F+`, `release 2F+`, `travel 3F+`, `contact 1F+`,
   `reaction 2F+`, `recovery 2F+` 또는 manifest가 정의한 동등 타임라인.
2. 투명 배경, 고정 canvas·pivot·anchor·발사점·접촉점.
3. frame별 독립 ImageGen key pose 또는 승인 원화를 기반으로 한 in-between.
4. contact frame에 SFX·햅틱·피해 숫자·reaction이 ±1 frame 안에서 일치.
5. 1×·2×·짧은 연출·저감 모션에서 판정 프레임 누락 0.
6. 390×844 실제 합성 영상과 48px 아이콘 접촉 시트.

기존 8프레임 공용 effect와 `enemy_wave`, 절차적 엉킴 몸체는 **C는 가능하지만 A는
prototype**이다. `care_vines-v2`와 `ledger_claw-v2`는 각각 단일 pose 원본 10장,
투명 runtime 10장, light/dark QA와 hash manifest를 가진 **production candidate**다.
실제 기기 contact 동기화·actor pose·profile 증거 전에는 production으로 승격하지 않는다.

P1 대표 세로 슬라이스는 뽀또의 고유 I 덩굴, 고유 II, 선택 I·II 아이콘, 돌비늘
장부지기의 장부 발톱, 적 hit/release, 플레이어·적 signature SFX까지 한 세트로
검수한다. 이후 같은
pipeline을 나머지 family에 복제한다.

스킬 슬롯 네 개를 잠그고(기본 공격·마음 지키기는 남겨 `최소 한 행동은 항상 합법` 불변식을 지킨다), 물결 종지기의 종은 그 전투의 집중력 최대치를 1 낮춘다. **앱 장착 화면 연결 완료** — `skill_book_screen.dart`가 두 칸의 현재 내용과 서고 전체를 함께 보여 주고, 서버가 준 `lock_reason`·`fell_back`을 그대로 문장으로 띄운다(위젯 9). 앱은 규칙을 다시 계산하지 않고 거부 사유도 서버 문장을 쓴다. 진입 경로는 **캐릭터 상세(3단계부터)와 출발 전 편성 두 곳**이며 전투 중에는 열리지 않는다(4.4의 `출발 전·캐릭터/스킬북 화면에서만 교체한다`). 위젯 10. **상점 구매 연결 완료** — 기록서를 기존 아이템 체계(`items.type='skill_book'`, 0036)에 넣어 구매 경로 11종(1등급 7 × 씨앗 40, 2등급 4 × 씨앗 120)을 상점에 올렸다. 보유의 단일 원본은 `user_skill_books`이고 `user_items`는 구매 사실만 남긴다(품종 해금과 같은 구조). 중복 구매는 씨앗을 차감하기 전에 막고, 해금·도전으로 이미 얻은 책도 재구매되지 않는다. **해금 판정 연결** — `plant_skill_mastery`(0037)가 여섯 행동 코드의 사용 횟수를 캐릭터별로 쌓고, 계정 합계로 `마음 지키기 누적 30회`(두 겹 잎방패)를 판정한다. 숙련은 위력·비용·쿨타임 어디에도 들어가지 않는다(11.6). 조건과 남은 진행도는 `GET /skill-books`의 `unlock_progress`로 사전 공개한다. 근거를 세는 기록이 아직 없는 조건(지역 깊은 조사, 약점 일치 30회 등)은 등록하지 않아 열린 척하지 않는다. 전투 기믹은 **7/20 연결**(전투 시작 3·행동 수치 2·전투당 1회 집중력 트리거 2). 수치는 전부 정액이고 `skill_book_effects.py` 한 곳에 모여 있으며, `combat.py`에는 호출 지점만 남는다. 나머지 13종은 새 전투 상태가 필요해(의도 공개·예고 대상 변경· 지연 버프·방어 이월·명령 순서 재배치) 별도 작업이다. command 7종은 선택 슬롯이 실제 행동이 되는 구조부터 필요하다. **선택 슬롯이 실제 행동이 됐다** — `command` 기록서는 7.5.1대로 대원 행동 1회를 쓰고, 집중력 비용은 등급을 따르며(1등급 0·2등급 1·3등급 2), 쿨타임은 자기 코드로 추적돼 전투당 한 번만 열린다. 전투 기믹 **12/20 연결**(command 4·opening 3·trigger 5). 다음 무언가를 기다리는 책의 대기 상태는 `state["skill_book_state"]` 한 곳에 모으고 JSON으로 왕복 가능한 값만 쓴다 — 잔향 읽기는 다음 라운드 예고를 `enemy.next_intent`로 열고, 약점 각인은 약점을 **실제로 맞힌** 공격 한 번에만 +3을 싣는다. 기믹이 없는 책은 슬롯에 이름은 보이되 `효과를 준비하고 있어요`로 잠긴다. **명령 `choice` 계약 완료** — 명령 요청에 `choice`(최대 48자)가 생겼고, 고를 것이 있는 슬롯은 `choice_kind`·`choice_options`(값+이름표)·`choice_current`를 함께 내려보낸다. **앱은 후보를 만들지도 규칙을 다시 계산하지도 않는다** — 목록이 두 곳에 있으면 어긋나고 사용자가 영문 없이 거절당하기 때문이다. 판정은 집중력을 쓰기 전에 하므로 잘못 고른 선택이 자원을 태우지 않고, 안 골랐거나 지금과 같은 것을 고르면 `EXPEDITION_COMBAT_CHOICE_REQUIRED`로 사유를 그대로 돌려준다. 첫 사용처인 마음결 조율기는 고른 결을 `member_state`에 얹어 **다음 공격 하나**에만 싣고 그 뒤 스스로 지운다. 상성을 `member_battle_kit`에서 다시 계산하므로 **확정을 누르기 전에 바뀐 상성과 늘어난 예상 피해가 보인다**(정면 18 → 약점 27). 이미 스스로 약점에 맞추는 프리즘 스킬은 덮어쓰지 않는다 — 덮으면 오히려 나빠진다. 비교 기준은 명령 스킬 자신의 결이 아니라 **그 대원이 평소 때리는 결**이다(감정 폼에 따라 둘이 다르다). AUTO는 사람이 골라야 하는 행동을 대신 고르지 않고 기본 공격으로 물러난다. **같은 계약으로 3등급 두 권까지 열었다** — 아홉 꼬리의 잔상은 예고된 공격을 고른 대원이 대신 받게 하고(그 대원은 그 라운드 `guard` 금지), 마음결 대백과는 첫 칸을 **출발 스냅샷에 얼려 둔** 보유 책으로 바꿔 낀다(바꾼 라운드 스킬 금지). 두 반대급부 모두 기본 공격과 마음 지키기는 남겨 `최소 한 행동은 항상 합법` 불변식을 지킨다. 후보는 `_battle_choice_context` 한 곳에서 만들어 **앱에 내려보낸 그 목록으로 판정한다** — 만드는 곳과 판정하는 곳이 갈라지면 화면에 보인 것을 골랐는데 거절당한다. 고를 것이 없으면(전체 공격이라 넘길 대상이 없다, 예비 기록서가 없다) 눌러 본 뒤 거절하는 대신 사유와 함께 미리 잠긴다. 파티 내 중복 금지는 전투 중 교체에도 적용되고, 바꿔 낀 책의 정액 수치는 실제로 붙는다(이름만 바뀌고 효과는 안 붙는 상태를 만들지 않는다). **남은 네 권까지 연결해 19/20** — `final_resolve`는 장벽 20% 이하에서만 기본 공격 +5(경계는 포함이고, 조건 판정은 서버가 해서 **누르기 전에 오른 위력이 보인다**). `steady_axis`는 적이 **전원을 노릴 때만** 정액 1을 덜어 내며, 단일 공격에는 붙지 않고 피해 상한을 적용한 **뒤에** 뺀다 — 상한 앞에서 빼면 상한에 먹혀 아무 일도 일어나지 않는다. `ringcount_record`는 파티 전원의 고유 II에 정액 +4를 싣고 장착자는 **그 전투 내내** 마음 지키기를 못 고른다(라운드가 아니라 전투 단위). `shadow_oath`는 장착자 한 명의 상성표를 갈아 끼워 약점 ×1.50 → ×1.70, 중립 ×1.00 → ×0.60으로 바꾸되 **내성은 덮지 않는다** — 설계서의 `원래 내성과 중복하지 않음`이 그 뜻이고, 덮으면 중립 0.60과 내성 0.60이 겹쳐 두 배로 아프다. 세 반대급부 모두 기본 공격을 남겨 `최소 한 행동은 항상 합법` 불변식을 지킨다. 전투 기믹 **19/20 연결**(command 7 전량·opening 5·trigger 7).

**`first_signal`(선제 신호)만 열지 않았다 — 설계와 현재 전투 모델이 어긋난다.** 효과 문장은 `적 의도 공개 후 1라운드 명령 순서 재배치`인데, 순차 명령 독(stage-battle-v2.0)에서는 **모든 플레이어가 이미 매 라운드 공짜로 하는 일**이다. 적 의도는 명령 전에 늘 공개되고(`enemy.intent`), 대기 중인 대원은 아무나 골라 아무 순서로 행동시킬 수 있다(`_selectMember`는 `awaiting`이기만 하면 통과). 이 책은 순서를 미리 제출하고 잠그던 **예약형 지휘 패널** 시절에 설계됐고, 그 패널이 교체되면서 팔 것이 사라졌다. 그런데 상점에는 씨앗 120으로 여전히 올라가 있다(0036) — **파는데 아무 일도 안 하는 항목**이라 출시 전에 정해야 한다. 효과를 다시 정의하거나 상점에서 내리기 전까지는 연결하지 않는다. 없는 효과를 있는 것처럼 잇는 쪽이 더 나쁘다. **0038에서 상점에서 내렸다** — `items.is_active=False`로 두어 목록과 구매가 함께 막힌다(`is_active`가 양쪽의 관문이다). **행은 지우지 않는다**: 이미 산 사람의 `user_items`가 참조하고 있고 구매 이력이 환불·문의의 근거다. 카탈로그도 같은 사실을 말하도록 `is_active`·`retired_reason`을 갖게 했고, 앱은 값 대신 이유를 보여 준다(살 수 없는데 `상점 씨앗 120`이라고 하면 어디서 사는지 찾아 헤맨다). 서고에서 지우지는 않아 이미 가진 사람에게는 그대로 남는다. 가드는 예외 목록이 아니라 **구조**다 — `is_active`가 곧 답이라 같은 상태의 책이 새로 생기면 목록을 고치지 않아도 바로 걸린다.

**해금 조건 진행도 4종 추가** — 근거를 세는 기록이 없어 비워 뒀던 조건 중 넷을 열었다. 조건마다 카운터 테이블을 새로 만들지 않고 `plant_skill_mastery` 하나에 함께 적되, 여섯 행동 코드와 섞이지 않게 `@` 접두사를 쓴다(접두 코드는 숙련 단계 계산에서 빠져 회상 문장이 오염되지 않는다). 근거는 전투가 **이미 싣고 있는 값**을 읽는다 — 새로 계산하면 판정과 기록이 어긋난다. `weakness_engrave`(장벽 3종)는 횟수가 아니라 **가짓수**를 세므로 `@barrier_kel:{결}`의 distinct 개수를 본다. `nine_tail_afterimage`(여우비 10회)·`shadow_oath`(그림싹 30회)는 `plant_species.code`로 조인해 **그 품종이 한 것만** 센다. `reviving_root`(안전 귀환 5회)는 `expedition_runs.status='safe_returned'`만 세고 도중에 물러난 `retreated`는 세지 않는다. 사전 공개는 6종(`GET /skill-books`의 `unlock_progress`).

**깊은 조사 3종은 여전히 등록하지 않는다** — `bellringer_chime`(우물정원)·`germination_gear`(보관고)·`ringcount_record`(관측실)는 모두 `깊은 조사 최초 완주`를 묻는데, 지금 구현에는 `deep` 모드가 없고(`tutorial|heart_resonance|free_explore`가 전부) 지역도 기억서고 하나뿐이라 **영원히 참이 될 수 없다.** 등록하면 진행도 0/1이 영영 멈춘 채 사전 공개된다. 깊은 조사 모드와 나머지 지역이 생기는 날 함께 연다. **남은 오디오 68종 완성** — 지역 ambience 8, 발걸음 4·발견 3, 품종 signature 32, 적 공격 signature 29. 전부 외부 샘플 없이 Python 합성이고 빌더·검수기가 짝을 이룬다. 문서의 20·24는 캐릭터·적이 늘기 전 수량이라 그대로 따르면 여섯 캐릭터와 다섯 적이 소리 없이 남는다 — **실제 콘텐츠 전부**를 만들었고 파일명은 서버 코드를 그대로 따른다. ambience는 A 32초/B 40초로 길이를 어긋내 겹친 반복 주기를 **160초**로 늘렸고, 이음매는 **원형 필터링**(버퍼 끝으로 필터 상태를 데운 뒤 전체를 거름)으로 만들어 경계 계단이 내부 변화량의 0.07~0.24배다(임계 3.0). 검수기는 통과 도장이 아니라 **설계 규칙을 숫자로 강제하는 장치**다 — 품종 signature는 `같은 품종 두 스킬 사이 거리 < 그 품종이 남과 갖는 최소 거리`를 요구해 소리로 캐릭터가 읽히는지를 구조적으로 검사하고(실제로 이 검사가 초기 설계의 결함 15건을 잡아 재료를 다시 갈랐다), 적 signature는 `오는 소리 < 맞는 소리`와 `전체 공격이 단일 공격보다 넓게 들림`을 강제한다. 발걸음은 같은 이름의 접촉음과 음량·밝기·길이 셋 중 둘 이상에서 갈려야 통과한다. 앱은 ambience 두 층을 각자 loop시키고(위치를 맞추면 길이를 다르게 둔 뜻이 사라진다) 전투에서 2dB duck한다. 번들 테스트가 68개 파일의 존재와 RIFF/ftyp 헤더를 확인해 하나라도 빠지면 실패한다.

**BGM 출처 기록의 끊긴 고리도 고쳤다** — `build_expedition_music.py --region all --check`가 `echo_well/base`·`heartwood_observatory/base` 두 곡에서 실패하고 있었다. 합성은 결정론적인데(같은 해시가 두 번 나온다) 기록된 master 해시가 달랐다 — 즉 **그 두 곡의 출시 파일을 현재 스크립트로 되살릴 수 없는 상태**였고, 이는 `마스터를 저장소에 두지 않고 스크립트+해시로 관리한다`는 정책이 막으려던 바로 그 일이다. 두 지역을 다시 렌더링해 고리를 이었다(런타임이 실제로 바뀐 것은 `heartwood-observatory-base.m4a` 하나뿐이다). **깊은 조사(`deep`) 모드 연결** — 설계서 9.2의 네 번째 난이도가 실제 모드가 됐다. **지역 8스테이지를 모두 마쳐야 열리고**(`UserStageProgress`를 그대로 읽는다 — 완주 플래그를 새로 만들면 두 값이 어긋나는 날이 온다), 잠긴 이유(`deep_locked_reason`)를 함께 내려보내 앱이 조건을 다시 세지 않는다. 잠긴 모드도 목록에는 남긴다 — 빼면 있는 줄도 모른다. 관문은 서버에 있어 요청을 직접 만들어도 `EXPEDITION_DEEP_LOCKED`로 막힌다.

난이도는 보스보다 **벽을 더 두껍게 하지 않는다**(장벽 12000 → 11500). 장벽만 키우면 전투가 길어지기만 하고 어려워지지 않는다. 대신 **한 방 상한을 6700 → 8400으로 올려** 예고를 잘못 읽은 대가가 실제로 아프게 만든다 — 실패가 숨은 확률이 아니라 `읽고 감수한 선택`에서 나오게 하는 장치다. 이 난이도는 **출발 시점 스냅샷에 굳어** 진행 중인 run이 나중의 밸런스 조정에 흔들리지 않는다(장착 스냅샷과 같은 이유). **보상은 늘지 않는다**(`reward_eligible=False`, `rules.deep_reward=False`) — 어려운 쪽이 벌이도 좋으면 편안한 난이도가 손해가 되기 때문이고, 2026년 사례(Splatoon Raiders)도 난이도가 적의 세기만 바꾸고 전리품은 바꾸지 않는 쪽을 쓴다.

**지역 깊은 조사 해금도 함께 열었다** — 근거는 새 카운터가 아니라 `expedition_runs`의 `mode='deep' · status='completed'`다(안전 귀환을 세는 방식과 같다). 다만 **콘텐츠가 실려 있는 지역만 사전 공개한다**: `shipped_region_codes()`가 콘텐츠 폴더를 훑어 답하므로, 지역 JSON을 넣는 날 코드를 고치지 않아도 조건이 저절로 나타난다. 지금은 기억서고 하나뿐이라 세 조건(우물정원·보관고·관측실)이 아직 안 보이는데, 이건 채울 수 없는 목표를 보여 주지 않기 위한 의도다. 기억서고의 보상인 `librarian_index`는 **탐험 공간 기록서**라 전투 전용 모듈(`skill_books.py`)에 넣지 않았다 — 넣으면 그 모듈의 `이 모듈은 전투 기록서만 담는다`가 거짓말이 된다.

**지역 콘텐츠 팩 3종 완성 — 네 지역이 전부 열렸다.** 먼저 **다중 지역 로더**를 만들었다(이게 진짜 병목이었다): `load_content()`가 파일 하나만 읽고 `catalog_payload`가 지역 하나만 내려보내던 구조라, 팩을 만들어도 실릴 곳이 없었다. 이제 지역을 인자로 받고, 모르는 지역은 **조용히 첫 지역으로 떨어지지 않고** 404로 막는다(진행 기록이 엉뚱한 지역에 쌓이면 안 된다). 파일 이름과 `region.code`가 다르면 시작 자체를 막는다. 카탈로그는 실린 지역을 전부 내려보내고 **앞 지역을 완주해야 다음이 열린다**(`EXPEDITION_REGION_LOCKED`).

팩은 기억서고와 **같은 뼈대**를 쓴다 — 8노드 그래프·8스테이지(전투 4·이벤트 2·쉼터 1·보스 1)·지도 템플릿 2종은 검증된 구조라 지역마다 새로 짤 이유가 없다. 지역이 다른 것은 **이야기와 재료**이므로 뼈대는 생성기(`scripts/build_region_packs.py`)에 한 번 적고 지역별로는 이름·문장·엉킴·수호자만 표로 준다. 수호자 셋은 **기록서 이름이 이미 정해 두었다** — 물결 종지기의 종 → 우물정원 **물결 종지기**, 발아 시계의 태엽 → 보관고 **발아 시계**, 나이테 관측 기록 → 관측실 **나이테 관측자**. 각 지역의 마지막 이야기는 다음 지역을 가리키고, 관측실은 온실로 돌아간다.

검증기가 만드는 동안 여섯 가지를 잡아냈고 전부 실제 결함이었다 — 전투 스테이지의 약점이 첫 엉킴의 첫 약점과 어긋남(이제 카탈로그에서 읽어 손으로 안 적는다), 회상마다 필요한 서고 항목 누락, 안전 선택이 연출·피해를 비워 둠(`안 정한 것`과 `0으로 정한 것`이 구분 안 됨), 마지막 보스 단계의 예고가 하나로 잘림, 발견 노드 코드가 `discoveries` 열쇠와 불일치, 단계 전용 예고의 기믹 누락. 그리고 **수호자 공격 코드가 엉킴 것과 겹치는 것**은 소리 빌더가 잡았다 — 코드는 소리·연출·기록의 신원이라 겹치면 둘이 같은 것이 된다. 이름을 갈라 주고 생성기에 겹침 검사를 넣었다.

**적 공격 signature도 38종으로 늘렸다**(엉킴 24 + 수호자 14). 빌더가 이제 **실린 지역 팩을 전부 훑는다** — 한 파일만 보면 지역을 실은 날 그 수호자만 소리 없이 남고 눈으로는 안 보인다. 번들 테스트가 14개 수호자 공격음의 존재를 확인한다.

**전투 스테이지 원고 12편도 다듬었다** — 생성기가 찍어 내던 `우물정원 3걸음 / 엉킨 것을 풀어 길을 넓혀요`를 지역별 문장으로 바꿨다. 어조는 기억서고를 따른다: 제목은 **자리나 사물**이고(번호를 읽어 주지 않는다), 요약은 **무엇이 어떻게 막고 있는지** 한 문장이다. 각 요약은 **그 자리에 실제로 나오는 엉킴을 가리킨다** — `매듭 사이에서 물방울이 튀어 올라`는 매듭진 메아리 + 튀는 물방울 떼가 함께 나오는 3스테이지의 문장이라, 예고와 화면이 어긋나지 않는다. 생성기가 뼈대 문장 복귀를 막는다: 원고 수가 전투 수와 다르거나, 제목이 번호를 읽어 주거나, 요약이 뼈대 문장 그대로거나 말투가 다르면 **생성 자체가 실패한다**. 구조는 찍어 내되 문장은 사람이 쓴 것이어야 한다는 선을 코드가 지킨다.

**지역 2~4 전용 원화 — 래스터는 못 만들었고, 받을 자리와 프롬프트를 만들었다.** 장면 원화 파이프라인은 ImageGen → 리사이즈 → WebP라 이미지 모델이 있어야 한다(오디오처럼 코드로 합성할 수 없다). 그래서 두 가지를 대신 했다.

**첫째, 코드가 원화를 받을 준비를 마쳤다.** `expeditionSceneTheme(sceneKey, regionCode:)`가 지역별 원화를 먼저 찾고 없으면 공용으로 떨어진다. 원화가 들어오면 `expeditionRegionSceneAssets`에 `{지역}/{장면}` 한 줄을 더하는 것으로 끝이고, **표에 적었는데 파일이 없으면 번들 테스트가 잡는다**(그 장면만 검은 화면이 되는 사고를 막는다).

**둘째, 그때까지 지역이 같아 보이는 문제를 색으로 갈랐다.** `expeditionRegionGrades`가 물빛·성에빛·나무빛을 원화 위에 얹고, 지역별 강조색이 테두리와 표시선을 바꾼다. 보정은 **원화 위·가독성 그라디언트 아래**에 둔다 — 글자 대비를 만드는 층을 건드리면 안 되기 때문이고, 알파를 0.20 미만으로 묶어 원화를 덮지 않는다(테스트가 강제). 첫 지역과 모르는 지역에는 걸리지 않아 기존 화면이 그대로다.

**셋째, 프롬프트 8장을 제작 규격대로 적었다**(`ADVENTURE_ASSET_PROMPTS.md`). 스물한 장을 다 만들지 않고 **재사용이 실제로 거슬리는 자리만** 골랐다 — 수호자 소굴 3(보스방은 가장 오래 보는 화면인데 수호자 넷이 같은 굴에 앉아 있다), 지역 입구 3(새 지역 첫 화면), 보관고 선반실·관측실 층계 2(각 지역의 상징 공간). 나머지는 색 보정으로 두고 뒤로 미룬다. 세 장이 공통 줄을 공유하게 적어 한 화면에서 이어 봤을 때 같은 세계로 읽히게 했다.

**원화 8장 생성·적용 완료(2026-08-13)** — ChatGPT ImageGen으로 1536×1024에 뽑아 `import_scene_art.py`가 1600×900 + 960×540 두 벌로 변환했다(3:2 원본의 위아래를 가운데 기준으로 잘라 16:9로 맞춘다 — 늘려서 맞추면 손으로 그린 선이 한 축으로만 늘어나 화풍이 무너진다). 여덟 장 모두 브리프대로 나왔고 라벨판의 글자 없음까지 지켜졌다.

**등록하면서 진짜 버그를 하나 잡았다** — `ExpeditionSceneBackdrop`에 `regionCode`만 넘기면 **색 보정만 바뀌고 전용 원화는 영영 안 나온다.** 그림을 고르는 것은 `expeditionSceneTheme(sceneKey, regionCode:)`이고, 호출부 다섯 곳이 지역을 안 넘기고 있었다. 이동 카드까지 포함해 전부 이었다 — 도착해서야 그림이 바뀌면 미리 보기가 거짓말이 된다. 그리고 **전용 원화가 있는 장면에는 색 보정을 얹지 않게** 했다(이미 그 지역 색으로 그려진 그림에 또 얹으면 두 번 물든다).

**원본 보관 정책은 오디오와 다르게 잡았다.** 오디오 마스터는 스크립트가 같은 바이트로 되살리므로 지워도 되지만, 이미지는 같은 프롬프트로도 같은 그림이 안 나온다. 원본 PNG(장당 2.3MB)는 저장소 밖에 두되 **원본 해상도 화질 95 WebP 사본 8장(3.2MB)은 추적한다** — 앱 산출물은 세로를 잘라 낸 것이라 크롭을 다시 잡으려면 사본이 필요하다.

**v2 3장 추가로 전용 원화 11장** — 남은 6조합 중 **글과 그림이 다른 말을 하던 셋만** 만들었다(보관고의 태엽 복도가 젖은 뿌리 굴로 나오던 것, 우물정원인데 우물 장면이 공용이던 것, `메아리 없는 방`이 보물고로 나오던 것). 나머지 셋은 주제가 이미 맞아 공용 원화 + 색 보정으로 둔다 — 여섯 장 다 만들면 셋은 낭비다. `scene_key`는 **슬롯 이름이지 그림의 약속이 아니다**: `root_tunnel` 자리에 시계 복도 그림을 넣어도 된다.

**검수에서 내 측정이 틀린 것을 잡았다.** `자글거린다`는 지적을 `이미지 − 흐린 이미지`의 전체 RMS로 확인하려 했는데, 이 값은 **또렷한 선과 자글거리는 질감을 구분하지 못한다** — 밝고 각진 그림은 잡티가 없어도 값이 커진다. 가장 깨끗하게 나온 보관고 입구가 이 척도에서 최악(10.46)으로 나와 멀쩡한 그림을 버릴 뻔했다. **타일별 중앙값**이 맞다(사람이 느끼는 것은 평균이 아니라 대부분의 면이 어떤가다). 이 척도로 보면 신규 11장은 1.44~7.54로 기존 원화(4.26~8.40)보다 조용하거나 같다. 재생성은 실제로 통했다 — 태엽 복도 **8.48 → 2.20**, 조용한 면 **1% → 63%**. 효과가 있었던 지시는 추상적인 `평평하게`가 아니라 **이미 잘 나온 그림을 가리키는 것**이었다.

**서고 화면에 발동 방식 글리프를 붙였다** — `아이콘 미제작`으로 남아 있던 자리다. 래스터를 새로 만들지 않고 Material 아이콘을 쓴다(장면 테마가 이미 같은 방식이라 화풍이 어긋나지 않고, 20권 × 등급 조합을 그림으로 그리면 관리할 자산만 는다). 서고에서 **가장 먼저 알아야 할 것은 효과가 아니라 `내가 눌러야 하나, 저절로 되나`**다 — 명령형은 대원 행동 한 번을 먹으므로 두 칸을 다 명령형으로 채우면 정작 때릴 사람이 없다. 글로만 적혀 있으면 스무 권을 다 읽어야 알 수 있었다. 테두리 색이 등급(3등급이 가장 두껍고 눈에 띈다 — 예산 2를 쓰는 대신 반드시 대가를 진다), 안의 그림이 발동 방식이다. 모르는 발동 모드는 **가장 조심스러운 쪽(눌러야 하는 쪽)으로 떨어진다** — 저절로 된다고 잘못 알려 주면 행동을 낭비한다.

**지도 위를 직접 걷는 이동(전면 도입, 1~3단계 중 1~2)** — 노드 탭 이동은 **없애지 않는다**(가상 스틱은 화면을 보고 손가락을 끄는 사람의 것이고 스크린리더 사용자에게는 쓸 수 없는 조작이다). 둘 다 남기고 마지막에는 같은 서버 `move` 호출로 모여, 간선·길빛 판정은 서버가 그대로 쥔다.

**스테이지 미니맵에도 같은 이동을 연결했다(3단계 완료)** — 이전에는 깊은 조사만
걸을 수 있고 8점 스테이지는 전투·사건으로 곧바로 들어갔다. 이제 4지역×8스테이지
모두 `들머리 → 실제 지역 랜드마크` 필드를 먼저 만들고, 캐릭터가 목적지 곁의 걸을
수 있는 자리에 닿아야 조우가 열린다. 전투·사건·쉼터·보스가 같은 진입 규칙을 지나며,
출발에서는 결말을 미리 말하지 않고 장·목적·현장 힌트만 보여 준다. 직접 드래그·표식
탭·스크린리더 대체 조작은 모두 서버의 동일한 `move` 판정으로 모인다.

**2026-08-18 타일 월드 교체** — 위 구현의 `지역 원화 위 토큰`은 실제 던전 안을
걷는 감각과 렌더 확장성 계약을 충족하지 못해 스테이지 경로에서 폐기했다. 스테이지는
이제 42×30(1,260칸)의 바닥 데이터, 물/벽/서가 충돌, 조형물, NPC, 몬스터, 보물,
아이템, 목적 이벤트를 별도 레이어로 가진다. 한 프레임에는 카메라 사각형에 걸친
타일과 오브젝트만 그린다(데스크톱 QA 시작 지점 209/1,260칸). 캐릭터 앞·뒤
오브젝트를 발 위치 Y로 나눠 가리고, 등불은 국소광, 화면 가장자리는 저주파 비네트,
발밑은 접촉 그림자로 처리한다. 오른쪽 위 미니맵은 전체 비트맵이 아니라 같은 저비용
월드 데이터의 축소 표시다.

ImageGen은 점묘/디더링/입자 노이즈를 금지해 바닥과 조형물 콘셉트를 만들었지만,
조형물의 `투명 배경` 결과가 실제 알파가 아닌 체크무늬가 구워진 `rgb24`임을 파일
채널 검사에서 잡았다. 이 결과를 억지로 크로마 제거하거나 런타임에 넣지 않았다.
출시 타일/조형물은 넓은 면·제한 팔레트·결정적 선/그라디언트로 그려 같은 입력에서
같은 결과가 나오고 점묘화가 생기지 않는다. 검수되지 않은 생성 이미지는 앱 에셋에
포함하지 않는다.

**2026-08-18 리토폴로지·텍스처 아틀라스 승격** — 초기 캔버스 원형을
96px RGBA 셀의 결정적 PNG 아틀라스로 굳혔다. 4지역마다 바닥 4·이끼 2·물 2·
해안 4·조형물/인물 9, 총 21종을 가지며 런타임은 한 장만 디코드한다. 가시 바닥은
`Canvas.drawAtlas` 한 묶음으로 그리고, 물 셀의 비물 인접면에 N/E/S/W 해안을
자동 합성한다. 조형물은 보이는 크기와 발밑 콜라이더를 분리하고, 플레이어의
0.28타일 원형 발자국을 최대 0.12타일씩 스윕해 얇은 장애물을 건너뛰지 못하게 했다.
4지역×8스테이지 출발점→제단 BFS와 아틀라스 768×1152/지역별 21셀 번들 검사가
회귀에 포함된다. 생성기 `--check`는 PNG와 JSON을 바이트 단위로 다시 만든다.

작업하며 **이미 있던 것과 없던 것이 갈렸다.** 경로 애니메이션·캐릭터 토큰·reduce-motion 처리는 이미 돌고 있었고, 제작 규격도 지도 토큰을 `72~112px, stage 2~4 transform`으로 이미 정해 두어 새 스프라이트 없이 붙일 수 있었다. 정작 없던 것은 셋이었다 — (1) 경로표가 기억서고 노드 이름으로 손수 적혀 있어 **새 지역 3개가 전부 직선으로 미끄러졌다**(간선 기하에서 굽은 길을 만들어 지역이 늘어도 코드를 안 고친다), (2) **발걸음 소리 4종에 호출부가 없었다**(만들어 두고 아무도 재생하지 않았다 — 이제 보폭 간격으로 울리고 재질은 장면이 정한다), (3) 토큰이 걷는 방향을 몰랐다.

**통행 영역을 볼록 다각형 하나로 잡은 것이 틀렸다.** 이 지도는 위에서 비스듬히 본 그림이라 걸을 땅이 한 덩어리라고 봤는데, 실제로 좌표를 넣어 보니 **개울 위(`.20,.13`)와 유적 안이 모두 `걸을 수 있음`으로 나왔다.** 지형 원화의 길은 랜드마크를 잇는 **그물**이라 한 덩어리로 감싸지지 않는다. 다각형을 겹쳐도 마찬가지였다 — 길이 곧지 않아서 열두 개로도 그림과 어긋난다. 벽에 부딪히면 **멈추지 않고 미끄러진다**는 것(축을 하나씩 나눠 시도)은 그대로 두었다. 멈추면 조작이 걸린 것처럼 느껴진다.

**그림자·명암은 스프라이트에 굽지 않고 코드로 얹는다.** 장면마다 광원이 달라서(우물정원은 위에서 푸른 달빛, 보관고는 서랍 하나의 따뜻한 빛) 구워 넣으면 어느 장면에서는 반드시 틀린다. 지역이 이미 아는 색(`expeditionRegionGrades`)을 캐릭터에도 얹고, 발밑 그림자는 걸음의 들썩임과 **반대로** 줄어 바닥에 닿았다 떨어지는 느낌을 만든다.

**그래서 그림에서 직접 읽는다.** `design-system/scripts/build_walk_masks.py`가 지형 원화 4장을 80×45 격자로 훑어 걸을 수 있는 칸을 뽑고, 결과를 `#`과 `.`으로 된 **글자 지도**로 다트에 박는다(`expedition_walk_masks.dart`). 격자 한 칸은 1600×900에서 20×20픽셀이라 화면에서 정사각형이고, 글자 지도라 사람이 눈으로 읽고 손으로 고칠 수 있다. 원화를 다시 뽑으면 생성기를 다시 돌리고, `--check`가 그림과 데이터가 어긋났는지 잡는다.

가르는 방법은 세 번 갈아엎었다. **밝기 하나로는 안 된다** — 밤 조명이라 수풀도 길만큼 밝다. **색 덩어리 대표색으로 나누는 것도 안 된다** — 그늘 진 길이 이끼 쪽으로 붙어 길이 토막 났다(덮개 16% → 0.2%). 지금은 **밝기 · 따뜻함(R−B) · 초록 치우침(G−R) · 채도**를 함께 보고, 빡빡한 문턱을 씨앗으로 삼아 느슨한 문턱을 **씨앗에 이어질 때만** 받는다(가장자리 검출의 이력 방식). 그늘진 길은 밝은 길에 붙어 있어 살아나고, 따로 떨어진 아치 지붕은 씨앗이 없어 들어오지 못한다. 형태학의 열기(침식→팽창)도 버렸다 — 길이 두세 칸 폭이라 침식 한 번에 좁은 구간이 통째로 사라졌다. **길은 원래 얇으므로 얇다는 이유로 지우면 안 된다.**

**노드 표식은 랜드마크 위에 찍힌다** — 아치 안, 우물 위, 나무 그루터기 한가운데다. 처음에는 그 자리를 걸을 수 있게 뚫었는데, 그러면 그루터기 위를 걷게 된다. 대신 **가장 가까운 길을 설 자리로 삼는다**(`expeditionStandPoint`). 랜드마크에 다가가는 것이지 올라서는 게 아니다.

**노드 사이의 길도 다시 만들었다.** 전에는 두 점을 잇고 가운데를 노드 코드 해시로 부풀린 굽이였다 — 굽는 방향이 그림과 아무 상관이 없었다. 이제는 마스크 위 A*로 찾고, 계단처럼 각진 것을 줄 당기기로 펴고, 모서리를 둥글린다. 셋 다 필요하다(칸 경로만 쓰면 톱니처럼 걷고, 펴기만 하면 각지고, 둥글리기만 하면 길 밖으로 나간다). 다듬는 과정에서 **여유를 잃은 점은 받지 않는다** — 안에 있기만 하면 된다고 두면 벽을 스치는 경로가 나오고 88px 토큰이 벽을 반쯤 먹는다.

검사는 구조적인 것을 본다 — **네 지역 43개 간선이 모두 걸을 수 있는 칸만 지나는가**, **노드마다 설 자리가 있고 표식에서 멀지 않은가**, **길이 벽에서 칸 반쪽만큼 떨어져 있는가**, 그리고 **그림에 없는 자리는 걸을 수 없는가**(개울과 지도 네 귀퉁이를 못 박아 둔다). 걸을 땅의 넓이도 본다 — 너무 좁으면 걸어 다닐 곳이 없고, 너무 넓으면 경계가 없는 것과 같다(현재 17~25%).

**지형 지도도 네 지역이 같은 그림을 쓰고 있었다** — `MossArchiveScene`이 기억서고 지형을 고정으로 썼다. 색 보정으로 덮어 두었지만 그 그림에는 보물상자 동굴·뿌리 둥지 같은 **기억서고의 물건**이 박혀 있어 색만으로는 다른 지역이 되지 않았다. 지역 지형 3장을 새로 받아 붙였고(1600×900 + 모바일 960×540, 품질 95 — 픽셀아트는 압축을 세게 걸면 같은 색 덩어리 경계가 뭉개져 우리가 만든 잡티가 생긴다), 남은 색 보정은 **지형 위·노드 아래**에 둔다(노드와 캐릭터가 함께 물들면 지도에서 읽기 어려워진다).

**색으로 못 가르는 자리는 손으로 막는다.** 비스듬히 내려다본 그림에서는 **세워진 면**이 바닥과 같은 색으로 칠해진다 — 별씨앗 보관고의 씨앗 서랍장과 대형 시계가 그렇다. 둘 다 벽면인데 바닥 돌과 밝기·채도가 같아서 문턱을 어떻게 잡아도 바닥으로 읽히고, 그 위에 서면 캐릭터가 벽을 타고 오른 것처럼 보인다. 지역표에 사각형 두 개를 적어 막았다. 이 목록이 길어지면 문턱이 잘못 잡힌 것이다.

**새 지역 3종을 실제로 걸어 보니 수호전 밸런스가 깨져 있었다.** 통합 테스트가 전부 기억서고만 쓰고 있어서, 생성한 지역은 **정적 검증만 통과하고 한 번도 플레이된 적이 없었다.** 출발 → 이동 → 수호전 → 목표 → 귀환을 실제로 지나는 종주 테스트를 붙이자 보관고·관측실에서 파티가 **졌다**. 세 가지가 겹쳐 있었다.

- **전체 공격 위력** — 기억서고 보스는 1인데 내가 만든 셋은 2~3이었다. 파티는 HP 5~6짜리 두셋이고 장벽은 난이도 계수가 붙어 156이라 여러 라운드가 필요한데, 전체 공격을 막으려면 그 라운드의 행동을 방어에 써야 해서 장벽을 못 깬다. **전부 1로 통일**했다.
- **방어 강요 기믹 중복** — `no_guard_action`은 세 방아쇠 중 유일하게 **행동 하나를 통째로 내놓아야** 꺼진다. 관측실에 둘을 달아 매 라운드 방어만 하다 끝났다.
- **위력 상승 기믹 중복** — 둘이 함께 켜지면 매 라운드 +2인데, 켜지는지가 **파티의 성장결이 그 약점과 맞느냐**에 달려 있다. 보관고 수호자는 기본 파티의 결이 마침 약점과 같아 **운으로** 통과하고 있었다. 하나로 제한했다.

세 상한 모두 생성기가 만들기 전에 막는다. 그리고 **패배를 조용히 통과시키던 내 단정도 고쳤다** — 지면 사건이 통째로 사라져 `battle.status`가 None이 되는데, 그것을 `승리 아니면 None`으로 받아들이고 있었다. 런 상태(`safe_returned`)로 봐야 한다.

종주 테스트는 노드 이름을 박지 않고 **지도를 읽어 최단 경로를 찾는다** — 지역이 늘어도, 지도 모양이 바뀌어도 그대로 돈다. 전투 AI도 앱 AUTO와 같은 수준으로 예고를 읽고 위험하면 방어한다(방어를 전혀 안 하는 기존 헬퍼로는 방어 강요 기믹을 단 수호자에게 반드시 진다 — 그건 콘텐츠가 아니라 시험하는 쪽이 비현실적인 것이다).

## 11. 이번 구현의 완료 정의

이번 작업은 전체 게임 출시가 아니라 첫 실행 가능한 수직 절편이다. 다음을 모두
만족하면 `S0-C`를 완료로 올릴 수 있다.

- 서버 응답에 고유 2·선택 2가 있고 여섯 행동이 실제 판정된다.
- 앱은 여섯 아이콘을 고정 순서로 보여 주며 평상시 스킬 이름·설명을 표시하지 않는다.
- 잠금·약점·비용은 glyph/숫자로 읽히고 48dp hit area를 가진다.
- 길게 누른 행동은 실행되지 않고 상세 시트만 열린다.
- AUTO가 네 스킬 중 합법적인 최선 행동을 선택하되 미래 정보를 읽지 않는다.
- 기존 `skill` 요청과 저장 중 run이 깨지지 않는다.
- 서버 전투 단위 테스트와 문서 링크·표·UTF-8 검사가 통과한다.
- Flutter SDK가 있는 환경에서는 관련 위젯 테스트와 `flutter analyze`가 통과한다.
